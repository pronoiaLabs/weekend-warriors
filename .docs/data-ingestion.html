Ingesting NFL data from BallDontLie

A design for loading the BallDontLie NFL API into Snowflake with dlt, grounded in live calls against our own key rather than in what the OpenAPI document claims.

The dlt-snowflake-template exists to get a pipeline running in Snowflake quickly. It is a starting point written in Python, not a framework to be worked around. Where its assumptions do not fit this source, we change it. Several places in this design do exactly that, and each one names the file and the edit.

Everything asserted here about the API was verified by calling it. Where the spec and the live response disagree, and they do, the live response wins.

Sources: .docs/openapi-meta/nfl.yaml, live calls against api.balldontlie.io on the GOAT plan, the template at dlt-pipelines/, and the dlt gameplan under dlt-pipelines/docs/development-gameplan/.

01

The API surface

Twenty-two endpoints under https://api.balldontlie.io/nfl/v1/. Every response is an envelope with rows under data, so every resource needs data_selector: data. Without it dlt loads the wrapper as a single row.

Authentication is a header named Authorization. Tested directly: the raw key returns 200, and Bearer <key> also returns 200. The API accepts either form, so dlt's bearer shortcut and the explicit api_key form both work. No auth returns 401.

YAML
      client:
        base_url: "https://api.balldontlie.io/nfl/v1/"
        auth:
          # both forms verified working; api_key is the more literal one
          type: api_key
          name: Authorization
          location: header
          api_key: "secret:sources.nfl.api_key"

The endpoints fall into four families: reference data (teams), directories (players), events and measurements (games, stats, plays, standings, season_stats, the advanced_stats trio, the team-stat pair, player_injuries), and betting markets (odds, odds/opening, and the two player-prop endpoints).

02

Cursor pagination, and where it isn't

Confirmed live: paging is cursor-based. A call to games?per_page=2 returns meta: {next_cursor: 423946, per_page: 2}. The request carries cursor and per_page. per_page caps at 100 and defaults to 25, so raising it cuts request count fourfold.

YAML
      paginator:
        type: cursor
        cursor_path: meta.next_cursor
        cursor_param: cursor

Two endpoints were verified to return no meta object at all: teams (32 rows) and standings?season=2025 (32 rows). The roster endpoint behaves the same way. Give those paginator: single_page so the intent is explicit rather than relying on a missing field to halt the loop.

One spec contradiction stands

odds/player_props documents no pagination and a meta carrying only per_page, yet the spec's own example shows a populated next_cursor. Worth a direct check before that endpoint is wired up. It is not in the first wave.

03

Rate limits, measured

The OpenAPI document says nothing about rate limits. The response headers do:

HTTP
x-ratelimit-limit: 600
x-ratelimit-remaining: 599
x-ratelimit-reset: 1785462831     # unix ts, ~62s out

600 requests per minute. Successive calls decremented remaining by one each while reset stayed roughly 60 seconds ahead, which is a fixed one-minute window. At 100 rows per request that is 60,000 rows a minute, comfortably more headroom than any of our loads need.

Retry behaviour needs no work from us. dlt's request client already retries on 429 and 5xx with exponential backoff, and honours Retry-After when present. The defaults are five attempts with a backoff factor of one, tunable without touching code:

TOML
# .dlt/config.toml, or as RUNTIME__* env vars in the SPCS spec,
# which avoids an image rebuild since config.toml is baked in
[runtime]
request_max_attempts = 10
request_backoff_factor = 1.5
request_max_retry_delay = 30

Worth capturing x-ratelimit-remaining into the observability table once the pipelines are running in parallel. The hook point is the rest_api branch of build_source, where a response hook can be attached in Python.

04

Everything is reachable

The spec flags three endpoints as requiring the GOAT tier. We are on GOAT, and all three were called successfully:

  • teams/1/roster: 200, where the spec documents a 403 for lower tiers.
  • odds/opening?season=2025&week=8: 200.
  • odds?season=2025&week=8: 200, returning rows with a populated updated_at.

So tier access is not a design constraint. What remains are the coverage windows, which are stated in prose and are not enforceable from the schema: roster data begins with the 2025 season, odds begins at 2025 week 8, and the two opening endpoints cover only the most recent completed season onward.

Empty is not an error

A request outside a coverage window returns an empty data array with a 200. Nothing raises. A pipeline scoped to the wrong season will report a clean, successful load of zero rows, so row counts in _DLT_RUNS are the signal to watch, not exit codes.

05

dlt already tracks every row

Declaring a primary key is a choice, not a requirement. dlt stamps lineage columns onto every table it loads, and those columns are enough to reconstruct history for a source that has no natural key.

  • _dlt_load_id: on every row, referencing _dlt_loads.load_id.
  • _dlt_loads: one row per completed load, with inserted_at and a status where 0 means success.
  • _dlt_pipeline_state: versioned incremental state, restored on fresh workers, which is what lets cursors survive ephemeral SPCS containers.
  • _dlt_id: a unique row id, and a content hash, but only under merge and scd2.

That last distinction matters. Under plain append, _dlt_id is not deterministic: loading the identical source row twice produces two different values. Deduplicating an append-only table on _dlt_id is a no-op. The join that does work:

SQL
select s.*, l.inserted_at as loaded_at
from raw_nfl.stats s
join raw_nfl._dlt_loads l on s._dlt_load_id = l.load_id
qualify row_number() over (
    partition by s.game__id, s.player__id
    order by l.inserted_at desc) = 1;

Last-write-wins over a keyless table, resolved downstream in dbt, with no key ever declared to dlt.

06

Four ways to load, and what each needs

The write disposition is the real decision. Only two of the merge strategies require a key at all.

  • append: insert, no dedup, no key. Every row carries its load id. The right default for immutable events.
  • replace: full refresh, no key. With staging-optimized plus enable_atomic_swap it is zero-downtime and preserves grants.
  • merge / delete-insert: needs primary_key and/or merge_key, either alone being sufficient. merge_key defines the delete scope without deduplicating, which is the canonical late-arriving-partition pattern.
  • merge / scd2: no key required. dlt hashes the row content into _dlt_id and maintains _dlt_valid_from and _dlt_valid_to. Change detection is hash against hash.

Merge with neither key does not error and does not corrupt anything. It degrades to append. Rows accumulate, which looks like duplication downstream, so it is worth being deliberate rather than accidental.

The scd2 retirement trap

With merge_key unset, scd2 assumes every run is a full extract and retires any row not present in it. Paired with a season-scoped extract, the first run would retire all prior history. Set merge_key to a partition column, game__id for stats, so retirement is scoped to what was actually fetched.

07

Choosing a disposition per endpoint

Live calls confirmed which endpoints expose an id and which do not. games, teams, and odds all carry one. stats and standings carry none, verified against real payloads rather than just the schema.

  • teams, replace. 32 rows, one request, no pagination. Nothing to be clever about.
  • standings, replace. 32 rows per season, no id, no meta. A full snapshot per run is cheaper than any incremental scheme.
  • games, merge on id. Scores mutate during play, so re-pull the season window and upsert.
  • stats, scd2 keyed by nothing and scoped by merge_key: game__id. No id exists, stat corrections land after the fact, and we want the history. This is precisely the case scd2 was built for.
  • odds, merge on id with an updated_at cursor. The one endpoint carrying a real modification timestamp.

The cursor on odds is worth being precise about. The API offers no "updated since" filter, so the cursor cannot shrink the request. It gives dlt a high-water mark and boundary deduplication, but the pull remains a full re-page of the window.

08

What the raw tables will look like

The API is inconsistent about references, and the split runs along family lines. Live payloads confirm it: a stats row nests game, player, and team as full objects, a games row nests home_team and visitor_team, and a standings row nests team. Meanwhile odds carries a bare integer game_id with nothing embedded.

dlt flattens nested objects with a double-underscore separator, so game.id becomes game__id. A stats row arrives very wide, with team and player attributes repeated on every row. That is fine. Conforming those into dimensions is dbt's job downstream, and reshaping during load would only make the raw layer harder to audit.

Snowflake identifier behaviour

dlt keeps table and column names lowercase in its schema, matching dbt's convention, while Snowflake casefolds to uppercase for case-insensitive identifiers. Also worth knowing: Snowflake does not enforce primary_key or unique. Uniqueness is guaranteed by dlt's merge logic, never by the database.

Two type inconsistencies to carry forward: plays.id is a string where every other id is an integer, and possession_time arrives as a "MM:SS" string rather than a duration.

09

The registry entry

A pipeline is declared, not written. Three fields are required, name, source, and a non-empty config, and the rest default. The full first entry:

YAML
  - name: nfl_reference
    source: rest_api
    dataset_name: RAW_NFL
    write_disposition: replace
    config:
      client:
        base_url: "https://api.balldontlie.io/nfl/v1/"
        auth:
          type: api_key
          name: Authorization
          location: header
          api_key: "secret:sources.nfl.api_key"
        paginator: single_page
      resource_defaults:
        endpoint:
          data_selector: data
      resources:
        - name: teams
          endpoint:
            path: teams

Two loader behaviours to keep in mind. Unknown keys are filtered out rather than rejected, so a typo takes the default silently. And the defaults: merge is a shallow dict.update, so an entry's config replaces the default wholesale.

The API key needs moving out of .env, which dlt does not read, into .dlt/secrets.toml under [sources.nfl] api_key, or exported as SOURCES__NFL__API_KEY.

10

When to stop using rest_api

The generic rest_api branch takes its config from a YAML blob that is serialised into a Snowflake VARIANT column. That works for declarative configuration and fails for anything that is a Python object: custom retry sessions, response hooks, computed columns, per-row transforms. None of those survive a JSON round-trip.

Note what this does not cover. Fanning out to a child endpoint, chaining one call into another, and scoping that chain incrementally are all native to the declarative config, verified on the fan-out page. None of them need custom code. The remaining gap is narrow: response hooks and per-row transforms, because both are callables.

So the moment we want rate-limit capture or a synthesised column, the answer is a dedicated source type rather than fighting the generic branch. Until then there is no reason to leave the declarative path. It is four edits when the time comes:

  1. Add the type.

    Append "nfl_api" to SUPPORTED_SOURCES in pipelines/batch/models.py.

  2. Write the source.

    A new pipelines/batch/nfl_api_source.py, modelled on the shipped sample_source.py.

  3. Dispatch to it.

    A branch in build_source in run.py, with the import inside the branch. Imports are lazy there on purpose, because CI import-checks the module with a minimal dependency set.

  4. Fix the smoke test.

    tests/test_registry_smoke.py hardcodes the source tuple. Import SUPPORTED_SOURCES instead of duplicating it.

Not in sources/

The top-level sources/ package looks like the extension point but is not copied into the SPCS image and is excluded from the installed package. A source placed there works locally and vanishes in Snowflake. Custom sources go under pipelines/. The CDC subsystem's lazy plugin registry is the pattern worth copying if this grows past one custom source.

11

One disposition per pipeline, for now

The runner passes the registry's write_disposition into pipeline.run(), and dlt applies that to every resource in the source. A per-resource disposition declared in the config is overwritten. Since the field defaults to merge and is never null, the override always fires.

Two consequences. First, teams as replace and stats as scd2 cannot share one entry today, hence one entry per endpoint. Second, the dict form of write_disposition that scd2 requires would fail validation, which only accepts the three plain strings.

Both are the same small fix, and it is worth making before the stats pipeline:

Python
# models.py: allow absent, and allow the dict form
write_disposition: str | dict | None = None

# run.py: only pass it when it is actually set
run_kwargs = {}
if spec.write_disposition:
    run_kwargs["write_disposition"] = spec.write_disposition
info = pipeline.run(build_source(spec), **run_kwargs)

With that, resource-level dispositions declared in the source survive, and a strategy dict can reach dlt. Two tests pin the old default and would need flipping to assert None.

12

Egress and secrets

Scheduled jobs need two things the batch path does not yet create: an external access integration so the container can reach the API, and a secret binding so it can authenticate. Neither is novel work. The CDC subsystem already ships both patterns, in sql/cdc/04_external_access.sql and sql/cdc/03_secrets.sql, ready to copy.

SQL
-- sql/prod/04_nfl_api_access.sql (new)
CREATE OR REPLACE NETWORK RULE DLT_DB.OPS.NFL_API_EGRESS
    MODE = EGRESS
    TYPE = HOST_PORT
    VALUE_LIST = ('api.balldontlie.io:443');   -- port is required

CREATE OR REPLACE EXTERNAL ACCESS INTEGRATION NFL_API_EAI
    ALLOWED_NETWORK_RULES = (DLT_DB.OPS.NFL_API_EGRESS)
    ENABLED = TRUE;

CREATE SECRET IF NOT EXISTS DLT_DB.OPS.NFL_API_KEY
    TYPE = GENERIC_STRING
    SECRET_STRING = '<key>';

The dev path already consumes both. make dev-run NAME=... SECRET=... ENVVAR=SOURCES__NFL__API_KEY EAI=NFL_API_EAI works today with no template changes. Only the scheduled path needs wiring: a secrets: block copied into the prod job template, and an EXTERNAL_ACCESS_INTEGRATIONS clause added to the emitted EXECUTE JOB SERVICE in generate_tasks.py.

One note on the setup target. make setup-prod applies an explicit file list, not a glob, so a new sql/prod/04_*.sql has to be added to it.

Every endpoint, grouped by what it needs

Twenty-two paths, of which three are single-item lookups (teams/{id}, players/{id}, games/{id}) already covered by their list equivalents. That leaves nineteen to load, and they sort into four groups by what the request has to supply.

  • Self-contained, no parameters: teams, players, players/active, player_injuries. Call them and they answer. Only teams and players carry an id.
  • Season-scoped: games, stats, standings, season_stats, team_stats, team_season_stats, and the three advanced_stats endpoints. One parameter each, bumped per backfill run.
  • Window-scoped: odds and odds/opening, which want season plus week, or a list of game ids.
  • Parent-resolved: plays and both player_props endpoints need a game_id, and teams/{id}/roster needs a team id in the path. None can be called without first knowing an id.

Two parameter details were wrong in my earlier reading of the spec and are worth stating plainly, because both return a 400 rather than an empty result. team_season_stats and team_stats use bracket syntax like every other array parameter: team_ids[] and seasons[], not the bare names the spec implies. And team_season_stats requires team_ids[], so it cannot be pulled for a whole league in one unfiltered call.

Row widths worth knowing

team_season_stats returns 195 columns per row and season_stats returns 63. At the other extreme player_injuries has four fields: player, status, comment, date. Only teams, players, games, plays, and the two odds endpoints expose an id. The other twelve need a merge scope rather than a key.

Fanning out from a parent

The four parent-resolved endpoints looked like they would force a custom source, since the registry cannot loop. They do not. dlt resolves a child parameter from a parent resource's rows declaratively, in the same entry, and the behaviour below was verified by running it rather than read off a page.

YAML
      resources:
        - name: games                # parent
          primary_key: id
          endpoint:
            path: games
            params:
              "seasons[]": [2025]
            incremental:
              cursor_path: date
              initial_value: "2025-01-01"
        - name: plays                # child: one call per game the parent yields
          endpoint:
            path: plays
            params:
              game_id: "{resources.games.id}"

There are two distinct syntaxes and picking the wrong one raises a ValueError at config-build time. A query parameter takes the inline string form shown above. A path parameter takes the type: resolve dict form, and dlt rejects that dict unless the parameter actually appears in the path template. Roster is the path case: path: "teams/{resources.teams.id}/roster" with teams as parent. There is also include_from_parent, which copies chosen parent fields onto child rows prefixed as _games_id.

Verified: the parent scopes the child

Running that config twice against a single 2025 game gave games=1, plays=197 on the first run and games=0, plays=0 on the second. Once the parent's watermark advanced it yielded nothing, and the child made no requests at all. Fan-out follows what the parent yields in that run, not everything it has ever seen, so an incremental parent scopes the child for free.

The cost is request count, and it is affordable. A game holds around 169 plays, measured against a real 2025 game, so a season of roughly 285 games is about 48,000 rows and 570 requests. Five seasons is under 3,000 requests, which is five minutes of a 600 per minute budget.

Props may not be backfillable

odds/player_props returned zero rows for a completed 2025 week 1 game and for a 2024 game. The provider states it keeps no history for props. Treat that endpoint as forward-only, captured as timestamped snapshots during the week, and do not plan a backfill for it.

Build order

Nineteen endpoints is not nineteen pipelines built at once. Four waves, each one proving a mechanism the next wave depends on.

  1. Wave 1: reference.

    teams then players, both self-contained and both keyed on id. Thirty-two rows and a few thousand. These prove auth, envelope unwrapping, and the Snowflake landing, and they give every later endpoint something to join to. players matters more than it looks: an injured player has no stats, so a stats-derived player list would break exactly the joins you care about.

  2. Wave 2: the season spine.

    games and stats. The first paginated entries, the first merge, and the first use of the seasons[] parameter that the whole backfill turns on. Run each twice and confirm the row count holds before going further.

  3. Wave 3: the rest of the season-scoped set.

    standings, season_stats, team_stats, team_season_stats, and the three advanced_stats endpoints. Same shape as wave 2, so these are mostly copies with a different path and merge scope. team_season_stats needs its team_ids[] list supplied.

  4. Wave 4: parent-resolved and market data.

    plays and roster via parent resolution, then odds and odds/opening, then player_injuries as a rolling snapshot. Props last, forward-only. This is the wave where request counts and coverage windows actually bite.

Backfilling five seasons, one at a time

The backfill covers 2021 through 2025, the five complete seasons. 2026 kicks off in September and is the first season to load incrementally. Splitting the two phases on a season boundary means there is nothing to reconcile between them: no game belongs to both, so the one real overlap risk disappears before it exists.

Not every endpoint reaches back five years, so the backfill runs to three different horizons:

  • Five full seasons: games, stats, plays, standings, season_stats, team_stats, team_season_stats, and the three advanced_stats endpoints.
  • 2025 only: roster. Earlier seasons return an empty array rather than an error, verified by asking for 2023 and getting zero rows back.
  • No history at all: player_injuries and players/active report current state only, and odds starts at 2025 week 8. Props keep no history whatsoever. These have nothing to backfill and simply begin accumulating from the first run.

One season per run, bumping the parameter each time. The delete scope is game__season, not season. Stats rows carry no top-level season field, only a nested game object, so the flattened column is what the merge key has to name.

YAML
    # no schedule during backfill: invoke by hand, one season per run
    write_disposition:
      disposition: merge
      strategy: delete-insert     # merge_key alone, no primary_key
    config:
      resources:
        - name: stats
          merge_key: game__season
          endpoint:
            path: stats
            params:
              "seasons[]": [2025]   # 2025, 2024, 2023, 2022, 2021

The sequence matters more than the speed:

  1. Load 2025 first.

    It is the season we probed, so the column list is known. Record the row count and the flattened column names before anything else runs.

  2. Re-run 2025 immediately, unchanged.

    The row count must come back identical. That single check proves the merge key is scoping the delete correctly, and it is far cheaper to learn now than after five seasons are in.

  3. Work backwards: 2024, 2023, 2022, 2021.

    One run each, checking the row count moves by a plausible amount and that the earlier season did not shift.

  4. Watch the older seasons for drift.

    dlt evolves the schema by default, so a season that introduces or drops a stat field will widen the table rather than fail. Compare column counts across runs so a silent addition does not go unnoticed.

Why not replace

Looping seasons with write_disposition: replace would leave only the last one. Each run truncates the entire table, so 2021 would wipe the four seasons loaded before it. The merge key is what makes season-at-a-time possible at all.

Cutting over to in-season runs

Very little changes at kickoff. The season parameter moves to 2026 and the entry gets a schedule. The disposition, the merge key, and the absence of a primary key all stay exactly as they were during the backfill. That is the point of settling the write strategy first: the cutover is a parameter change, not a redesign.

Games land in three blocks each week, so the pulls follow them the morning after:

YAML
    # Fri after Thursday night, Mon after the Sunday slate, Tue after MNF
    schedule: "0 12 * * 1,2,5"    # five cron fields, UTC, no timezone suffix

Noon UTC is 7am Eastern, comfortably clear of every game. Monday night football ends around 11:30pm Eastern, which is 04:30 UTC the following day, so an earlier slot risks catching a game still in progress and loading a partial box score.

Two ways to scope the request. Both are declarative, so the choice is now purely about stat corrections rather than about effort:

  • Season-scoped. Ask for "seasons[]": [2026] every run and re-pull the season each time. Roughly 400 requests against a 600 per minute budget. Corrections anywhere in the season self-heal, because every game is fetched again on every run.
  • Slate-scoped. Make games incremental on date and resolve the child from it. Only games past the watermark are yielded, so only those fan out. Around 20 requests instead of 400, and no custom code, as verified on the previous page.

The catch with slate-scoping is the mirror image of its efficiency: a correction to a game already past the watermark never gets re-fetched, because the parent will not yield that game again. The cheap answer is to run both. Slate-scoped on the 1,2,5 cadence for freshness, plus a season-scoped sweep once a week to sweep up corrections. Together they still cost well under a minute of the rate budget.

Either way, what changes between them is only how the request is scoped. The disposition, the merge key, and the absence of a primary key stay put.

Where this lands

The template is a starting point, not a contract. Where it does not fit this source, the fix is a few lines of our own Python.

The loop is: add an entry, dry-run it to DuckDB, inspect the flattened columns, run it twice to confirm the disposition behaves, then point it at a personal dev schema in Snowflake. A schedule goes on last, once the egress and secret objects exist.

Three template edits are on the path, and none are large: making write_disposition optional so scd2 and per-resource loads work, adding the EAI clause to the task generator, and copying the dev job template's secrets block into the prod one. A custom source type joins that list the moment we want rate-limit telemetry or computed columns.

Rate limits, tier access, pagination behaviour, and the presence or absence of id on each endpoint were all confirmed against the live API. Flattened column names should still be checked against a first real load.
