Internal reference · companion to the enrichment and APP/API docs

Semantic views built for conversation

The agent-facing tool roster, built on DIM/FACTS only — kept simple on purpose. A LangGraph orchestrator fronts everything, connected over MCP to Cortex agents that each master one discipline's semantic views. The report workflow and edge chat are the orchestrator's two modes; a screen-embedded play-log agent drives the film-study page as a sibling.

The decision: DIM/FACTS only

Semantic views sit on the star — facts with additive measures, dims with clean attributes, relationships doing the joins — never on APP marts. Why this holds even though APP encodes hard-won logic:
  • Aggregation safety. APP marts are full of non-additive columns (running to-date, trailing averages, ranks, hit rates). Generated SQL will happily SUM them. The star's metrics — defined once as ratios of sums — are the guardrail Cortex Analyst is built around.
  • Composability. The agent should answer questions no dashboard page renders. APP is pre-filtered and pre-shaped (completed games, vendor fan-out, offense-only); DIM/FACTS lets any grain aggregate any way.
  • Stable coupling. APP columns move with UI needs. DIM/FACTS is the contract layer — and because views resolve tables via ref(), the physical renames (PLAYER_PROFILE, PLAY_LOG, …) cost the views nothing.
  • Where APP logic is genuinely the definition (trailing windows, allowed splits), the agent gets the same answer a different way: the metrics and AI_SQL_GENERATION rules encode the same discipline (strictly pre-kickoff, sum-over-sum), and the situation view is built on the same fact the APP mart reads.

The orchestrator LangGraph → MCP → Cortex discipline agents → semantic views

The topology. A LangGraph agent is the orchestrator — the only thing users talk to. It connects over MCP servers to Cortex agents, each one a master of exactly one discipline, each discipline owning its semantic view(s). Four layers, strict responsibilities:
  • LangGraph orchestrator — routing, planning, cross-discipline reasoning, and composition. The report workflow and the edge chat are its two modes: a report is a planned fan-out (schedule + form + availability + market + props called in parallel, sections composed from their answers); an edge conversation is per-turn routing to whichever discipline the thread needs next. It owns conversation memory and never touches SQL.
  • Deterministic Postgres tools — anything with a known question shape is a plain LangGraph tool pinging the app_copy tables directly: a WHERE clause and an ORDER BY over precomputed columns, no LLM, no warehouse. The APP marts' non-additive columns — the reason semantic views avoid them — are exactly what makes them perfect tool surfaces: ranks, hit rates, gaps and trailing windows are pre-answered. Tool answers are byte-identical to what the app screens show, by construction.
  • MCP servers — each Cortex agent is registered as an MCP tool with a one-line contract: what discipline it masters and what a good question to it looks like. The orchestrator's tool-selection quality lives or dies on these descriptions, so they are written like the view comments: specific, bounded, honest about coverage.
  • Cortex discipline agents — one per discipline, each a deploy_* macro like nfl_analyst today (spec inline, <<DATABASE>> tokens, alter-mode updates). A discipline agent answers only from its own views; it never reaches across. Cross-discipline synthesis ("is his line out of step with his usage?") is the orchestrator's job — it screens the prop board with the tool, asks the player analyst why, and reasons over both answers.
  • Semantic views — the roster below, unchanged. Verified queries stay with the discipline that owns them, which is what makes each agent a master: its verified queries are its craft.
The play-log agent stays a sibling, not a Cortex agent — it drives the API layer on its screen. The orchestrator hands off to it ("want to see those plays?") rather than wrapping it.

The roster deterministic Postgres tools first, Cortex agents where reasoning is required

The split rule — and the funnel it serves If the question is a WHERE clause and an ORDER BY over precomputed columns, it's a tool pinging Postgres. If it needs novel aggregation or judgment, it's a Cortex agent over the star. And the orchestrator's questioning is geared toward one thing: identifying plays. The funnel is: screen the slate and the boards deterministically (tools — cheap, exact, instant) → explain the survivors analytically (agents — why is the usage rising, is the matchup real) → price-check deterministically (tools again) → surface the play. Tools do the volume; agents do the judgment; the LLM never re-derives what a table already holds.

Design rules that keep the roster honest Schedule, news and status questions turned out to be fully deterministic — they have no Cortex agent at all, just tools. That leaves sv_nfl_schedule and sv_nfl_player_news without a discipline owner: they stay deployed for the general fallback below, and become retirement candidates once the tools prove they cover the whole question space. Every remaining agent owns one discipline and one to two views; the orchestrator owns every cross-discipline thought and the tools-vs-agent routing. When a question keeps arriving at an agent with the same shape, that's a signal to promote it to a tool (add the precomputed column to the APP mart if needed) — the roster's center of gravity should drift deterministic over time. The existing all-in-one nfl_analyst survives as the general fallback until the roster covers it, then retires deliberately, with a date. Verified queries stay with the discipline that owns them — mastering a discipline means owning its canonical answers.

Nice to have — the page-aware edge agent the multiplier: from destination to layer over the whole app

The edge agent rides along on every page, not just a chat screen:
  • Context in. Each request carries page context — route, entity in view, active filters — so "is this line beatable?" asked from a prop row needs no re-explaining. The orchestrator receives the page context as part of every turn.
  • State out. The agent can write back: the play-log agent's Postgres session pattern generalized into per-page state configs (active filters, selected vendor, pinned entities) that the pages already read — so an answer can repopulate the screen the user is on. "Show me that on the board" flips the filters instead of describing them.
  • One mechanism, not many. A page-state table beside app_copy plus a state endpoint per page, riding the same session machinery as play-log v2 — building the play log's session store is also building this.

Mechanics the constraints that hold for every view here

Metrics discipline
Metrics only on additive columns; every rate and share is a ratio of sums (total EPA / total plays, total targets / total team targets), never an average of per-game rates. NULL-vs-zero semantics ride in from the wide facts: NULL means no vendor match or preseason, and AI_SQL_GENERATION says so per view.
DDL & deploy
Clause order is enforced: TABLES → RELATIONSHIPS → FACTS → DIMENSIONS → METRICS → COMMENT → AI_*, with AI_VERIFIED_QUERIES last. Views resolve tables via ref(), so the DIM/FACTS physical renames cost nothing here. Agents stay macros (deploy_<name>, <<DATABASE>> tokens, --args "'{alter: true}'" quoting through snow dbt execute). SQL-generation rules live in the view's AI_SQL_GENERATION clause, never in agent instructions.
Rollout per view
Each changed view ships with: the metric additions, refreshed AI_VERIFIED_QUERIES (the report agent's building blocks — every report section keeps a canonical verified query), an agent-instruction touch only if the tool list itself changed, and a dev build + deploy-sport like everything else. Phase alignment: player/team metric enrichment after Phase 2; availability after Phase 1–2; situation after Phase 3.
