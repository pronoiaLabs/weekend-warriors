Internal reference · companion to the APP & API plan

The screens, and the tables behind them

The app is built around one journey: land, catch up on the tea around the league, then go fishing for players — at game level or player level. This doc names every screen, the zones on it, the APP table feeding each zone, the API route serving it, and the image assets (headshots, logos, colors) that make it feel like a real product.

The journey what a session actually looks like

Three modes, in order. Every screen exists to serve one of them, and every screen links forward into the next.
  • Catch up. First minute on the app: what happened since I last looked? Injuries and designation changes, the hot topics, who the fantasy world is grabbing and dropping, which lines moved. One screen — the Pulse — answers all of it, and every item on it is a door into fishing.
  • Go fishing. Two lanes into the same water. Game lane: start from the slate, pick a matchup, and work the pond — what does this defense give up, in which situations, and which props sit soft against it. Player lane: start from the finder, filter by position and usage, and work a player — form, situational usage, projections against lines.
  • Dig in. When a candidate surfaces, drop to the play log and watch the pattern at play grain — with the embedded agent driving the screen through the API. The edge agent overlay rides along on every screen for the questions that need judgment.
Fishing is the product; catch-up is the bait. Nothing on the Pulse is a dead end. A news item opens the player it names. A designation change opens the depth chart it shakes and the props it moves. A trending player opens their detail page. A line move opens the market view. The screen map below is drawn so that every arrow points toward a decision about a play.

The screen map every screen, and how you move between them

Solid arrows are the journey's main current; dashed arrows are the cross-lane jumps that matter most — a prop board row opens the player behind it, and a game card can drop straight into the play log filtered to that matchup. The supporting screens (teams, markets, explorer) stay in the global nav; they serve deeper digs rather than the main current.

Fishing hooks

trending player → player detail

Why these four signals
They are the four ways an edge announces itself before kickoff: the press knows something (news), the team confirmed something (status), the crowd smells something (trending), and the books already repriced something (movers). Seeing all four side by side is the catch-up; clicking through is the fishing.
STATUS_BOARD and TRENDING_PLAYERS are buildable now — fact_injury_report, fact_depth_chart and fact_sleeper_trending already exist. MARKET_MOVERS derives from the two snapshot facts. Details in new marts & routes.

Fishing hooks
The screening pass
Sort the prop board by projection-minus-line delta, filter to positions the defense-allowed grid flags as leaky, and check the situation splits for why (bad on third-and-long, generous in the red zone). That is the deterministic screen; the plays that survive move to the player lane.

Supporting screens the deep-dig surfaces, reachable from anywhere

TEAMS

exists, grows · GET /api/nfl/teams + /teams/{team} · standings, weeks, allowed, ATS, situations
Standings with home/away splits and planned EPA columns (TEAM_STANDINGS); the team page stacks week-by-week with EPA blocks (TEAM_WEEKS), the allowed-by-position grid (TEAM_ALLOWED), against-the-spread history (TEAM_ATS), and the new situation splits array (TEAM_SITUATION). Branding lands here hardest: logos in standings rows, team colors as page accent on the team page, opponent logos in the week log. Doors: week row → game detail; allowed cell → prop board filtered to that position; situation cell → play log.

MARKETS

exists · GET /api/nfl/markets + /markets/{game_key} · LINE_HISTORY + PROP_LINE_HISTORY
Line movement over the collapsed snapshot facts — a row means the line moved. The Pulse's market-movers zone is the summary; this is the full curve. Unchanged by this plan except arrival context: movers deep-link here with game and market pre-selected. Deferred idea from the APP & API plan stays deferred: overlaying projection history on the prop-line curve.

EXPLORER

exists · GET /api/nfl/explore + /explore/{sheet} · all EXPLORE_* sheets
The escape hatch when a curated screen doesn't cut the question: flat sheets with live column lists, filter, sort, export. Gains the planned team_situations, plays (v1 play log), and player_situations sheets — the v1 way to fish at play grain before the pattern room ships. Zero-code on new columns by construction.

EDGE AGENT OVERLAY

nice-to-have · every screen · see the semantic views plan, "page-aware edge agent"
The edge chat agent rides on every screen as an overlay dock. Each request carries page context (which screen, which filters, which entity), and the agent can write Postgres page-state configs to populate the screen it's sitting on — ask it "show me this week's soft WR props" from the pond and the prop board re-sorts itself. Designed in the semantic views plan; this doc just reserves the dock on every screen so wireframes account for it.

What we have

NFLVERSE_PLAYER_STATS.HEADSHOT_URL carries the same asset at week grain
URL shape
https://static.www.nfl.com/image/…/f_auto,q_auto/league/{id}
The NFL's Cloudinary-style CDN: f_auto,q_auto in the path means the CDN negotiates format and quality, so the same URL serves list chips and the big player-detail portrait. Store the URL as-is; no resizing pipeline needed on our side.

Branding is static per season, so the frontend fetches it once, caches it, and joins client-side by team_key — which every mart already carries on both home/away and team columns. This keeps logo/color columns off every other mart and every other row model: zero LINE_FIELDS-slice risk, zero fixture churn on marts that would otherwise all gain five columns.
Dark mode
Team colors on dark panels can fail contrast (navy on near-black). The wireframes should treat color_primary as an accent behind a contrast check, with logo_squared_url as the safe mark on any background — that's what it exists for.

Hotlinking reality check. All three hosts (static.www.nfl.com, ESPN's CDN via nflverse, sleepercdn.com) serve these URLs publicly today and the nflverse ecosystem has leaned on them for years — but none is a contracted asset service. For a personal app that risk is fine to accept; the mitigation to keep in the back pocket is a one-time mirror of logos/wordmarks (a few hundred small files) into our own bucket if a host ever tightens up. Headshots are too many to mirror casually; the initials fallback covers an outage.

Wireframes next docs/screens/ — one file per screen, this theme

The next step is visual: a docs/screens/ folder, one self-contained HTML wireframe per screen, using the same theme tokens and light/dark behavior as these docs, with static sample data shaped exactly like the API payloads named above.
  • Build order follows the journey: the Pulse first (it defines the app's voice), then game detail · the pond (the densest screen), then player detail, then the play log pattern room. Game day, players, and the supporting screens fall out of the patterns those four establish.
  • Each wireframe carries its data contract: a footer note naming the route and marts feeding each zone, so a wireframe review doubles as an API-payload review.
  • Every screen reserves the agent dock (bottom-right overlay) so the edge agent lands without a redesign.
  • Assets render for real: wireframes use live headshot and logo URLs from the warehouse rows above, because layout decisions (chip sizes, contrast, fallbacks) only surface with real images.
