Chapter 4

Scheduling containers with nothing but Snowflake Tasks

the registry-driven ingestion pattern

Every pipeline in this project runs on a schedule with no Airflow, no cron box, no GitHub Actions timer, nothing outside the Snowflake account. The scheduler is the humble Snowflake Task, and the whole design of the ingestion layer falls out of one property of that object that sounds like a footnote until you build against it: a Task passes no arguments.

§ 1. The constraint that shapes everything

There is no command line at 09:00 UTC. When a Task fires, it runs the SQL in its own body and that is all it can do. No --resource, no --param, no season flag, nobody watching. Everything a run needs must either be written into the Task's DDL ahead of time or be discoverable by the container once it is up.

You can fight that constraint with wrapper procedures and config tables full of overrides, or you can lean into it. I leaned in. The design is a registry: one YAML entry per pipeline in dlt-pipelines/pipelines/batch/registries/, merged into a single registry and synced to a control-plane table that the container reads at runtime. The runner, the Task generator, and the observability layer all read the same record. A registry entry that carries a schedule field becomes a Task; one that does not is skipped with a comment, which is how the smoke-test pipeline stays runnable by hand without ever becoming a production schedule. Not scheduled is expressed by omission, never by a flag.

Listing 1 · a registry entry, trimmed to what scheduling reads

defaults:
  database: NFL                       # a stem: resolves to NFL_PROD_DB when scheduled
  load_warehouse: DLT_WH
  compute_pool: DLT_POOL
  secret: DLT_DB.OPS.NFL_API_KEY      # Snowflake SECRET holding the API key
  env_var: SOURCES__NFL__API_KEY      # env var the container reads it through
  external_access: NFL_API_EAI        # egress to the source API

pipelines:
  - name: nfl_games
    schedule: "0 9 * * *"             # daily, after Monday Night Football ends
    config:
      resource_defaults:
        endpoint:
          params:
            seasons[]: "{current_season}"   # resolved at run time, see § 3

From dlt-pipelines/pipelines/batch/registries/nfl-registry.yml: the schedule, the credential binding, and the egress path all live on the same record.

The validation is deliberately strict about the combination: a registry entry declaring a schedule without secret, env_var and external_access fails the test suite, because the alternative is a container dying at 09:00 UTC looking for a credential nobody bound. (How the image, spec and secrets themselves work is Chapter 1's story; this chapter is about who pulls the trigger.)

§ 2. What the generator emits

The generator, dlt-pipelines/deploy/tasks/generate_tasks.py, emits one CREATE OR ALTER TASK per scheduled pipeline. It prints SQL rather than applying it: Task DDL is reviewable, diffable and re-runnable only if it exists as text first, and a generator that also executed would make every dry run a production change. Each Task carries a cron schedule and wraps EXECUTE JOB SERVICE with the container spec rendered locally and inlined into the DDL. There is no stage read at run time; the emitted SQL states exactly what will run.

Listing 2 · one emitted Task, trimmed

CREATE OR ALTER TASK DLT_DB.OPS.dlt_task_nfl_games
  WAREHOUSE = DLT_WH
  SCHEDULE = 'USING CRON 0 9 * * * UTC'
AS
  EXECUTE JOB SERVICE
    IN COMPUTE POOL DLT_POOL
    COMMENT = 'nfl_games'
    EXTERNAL_ACCESS_INTEGRATIONS = (NFL_API_EAI)
    FROM SPECIFICATION $$
spec:
  containers:
    - name: dlt
      image: /DLT_DB/DEPLOY/IMAGES/dlt-pipeline:latest
      args:
        - nfl_games
      env:
        DESTINATION__SNOWFLAKE__CREDENTIALS__DATABASE: NFL_PROD_DB
        SNOWFLAKE_DATABASE: DLT_DB
      secrets:
        - snowflakeSecret: DLT_DB.OPS.NFL_API_KEY
          secretKeyRef: secret_string
          envVarName: SOURCES__NFL__API_KEY
$$;

-- ALTER TASK DLT_DB.OPS.dlt_task_nfl_games RESUME;   -- uncomment to start

Cron, compute pool, egress, secret binding and target database, all derived from the one registry entry in Listing 1.

Two details in that listing cost me real debugging time. First, there is no NAME = on the job service, and that is deliberate. Second, the EXTERNAL_ACCESS_INTEGRATIONS clause sits before FROM, and it has to: EXECUTE JOB SERVICE fixes its clause order, and putting the integration after the specification is a SQL compilation error, not a warning. Worse, the error only fires for pipelines that pass an integration at all, so a source needing no egress hides the mistake entirely. There is a test in dlt-pipelines/tests/test_tasks.py that asserts the ordering on every emitted Task, because this is exactly the kind of thing that is cheap to check as text and expensive to discover in TASK_HISTORY.

Hard-Won Fact

A fixed job-service NAME collides on the second run. A completed job service persists for 30 days so its logs stay readable, and there is no OR REPLACE on EXECUTE JOB SERVICE. A daily Task with a fixed name succeeds on the first morning and fails with "Object already exists" every morning after. Omit NAME, let Snowflake generate a unique one per run, and put the pipeline name in COMMENT so SHOW SERVICES can still tell you what each job was.

The Task name itself is fully qualified (DLT_DB.OPS.dlt_task_<pipeline>) because the grant is CREATE TASK on that specific schema and nothing guarantees the applying session has a current schema at all. And the target database is always the prod one: a Task is the production schedule, so the generator simply cannot emit a dev target. The tests enforce that too, with a literal assert "_DEV_DB" not in sql.

§ 3. What a Task cannot pass, and the season problem

The sharpest edge of the no-arguments rule is the season parameter. The source API is inconsistent about it in the worst way: /standings and the advanced-stats endpoints return HTTP 400 without a season, while /games and /stats silently return every season the API holds. So a scheduled run without a season is either a loud failure or, much worse, a green run that quietly re-fetched years of history it did not need.

Since no argv exists, the season goes into the registry as a token: season: "{current_season}". The runner substitutes the real year before dlt ever sees the config, using a rule that rolls over on 1 August when preseason opens, so January stays on the season still being played. A hardcoded year would work until the August nobody remembers it, and then every nightly load would report success while fetching a season that ended months ago. The token fails toward the correct behavior instead.

Backfills are unaffected, because manual runs do have a command line: a --param season=2023 merges in after the token resolves and wins. Nothing about scheduling changes how you load history, which is precisely what you want from a scheduling layer.

§ 4. The reapply dance

CREATE OR ALTER TASK has two behaviors that matter here, and they bite at different moments. It refuses to touch a Task that is started, failing with error 091421 and changing nothing. And once it can apply, it leaves the Task suspended, so a successful reapply silently stops the schedule. Together they mean applying changes to a running fleet is always three steps, never one.

Listing 3 · the three generator outputs, applied in order

python -m deploy.tasks.generate_tasks --suspend
  # ALTER TASK IF EXISTS DLT_DB.OPS.dlt_task_nfl_games SUSPEND;

python -m deploy.tasks.generate_tasks
  # CREATE OR ALTER TASK ... (Listing 2, once per scheduled pipeline)

python -m deploy.tasks.generate_tasks --resume
  # ALTER TASK DLT_DB.OPS.dlt_task_nfl_games RESUME;   -- no IF EXISTS

Suspend, apply, resume: all three gate on the same spec.schedule field, so they can never disagree about which pipelines are Tasks.

Hard-Won Fact

snow sql -f stops at the first error. Apply task DDL to a fleet whose first Task is started and the file aborts before the rest are attempted: some Tasks carry the new spec, some the old, and nothing in the output says which half is which. Measured against a live 17-Task fleet. The suspend pass exists so this state cannot be reached.

The asymmetry between the two ALTER passes is deliberate. Suspend uses IF EXISTS because it runs before the apply, when absence is expected: on a first deploy no Task exists yet, and a bare ALTER TASK would abort the suspend pass on the first missing name and leave the rest started, reproducing the exact problem it prevents. Resume does not use IF EXISTS, on purpose. It runs after the apply created every Task, so a missing Task at resume time means the apply failed partway, and the error is the only signal that would ever say so.

Hard-Won Fact

Tasks are emitted suspended, and the resume is a separate, deliberate step: generating a schedule and starting one are different decisions. That default is right for a human reviewing DDL and a trap for CI, which reapplies on every registry change and would stop the fleet each time. Hence --resume as a second output CI applies immediately after. And verify with SHOW TASKS, never the exit code, because a suspended fleet looks exactly like a successful deploy.

§ 5. The punchline

Here is what all of this buys. Adding a pipeline is one YAML entry. The same record tells the runner what to fetch, tells the generator what Task to emit (cron, pool, warehouse, egress, secret binding, target database), and tells the observability layer what to attribute the run to. There is no second config file to update, no DAG to edit, no deploy manifest to keep in sync with the registry, because there is only the registry. The constraint that started this chapter, a Task passes no arguments, is what forced everything onto one record, and the one record is why the whole thing holds together.
