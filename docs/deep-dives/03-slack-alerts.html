Chapter 3

Slack alerts with zero external infrastructure

and the two-day silent outage that demanded them

The outage that motivates this chapter started as routine work: I redeployed the dbt project object for one of the sports. Models had changed, the triggers run whatever the object holds, so you deploy and move on. What I did not appreciate at the time is that snow dbt deploy --force is a CREATE OR REPLACE under the hood, and replacing an object in Snowflake drops the grants on it. The triggered task that runs the prod builds executes as DBT_RUNNER_ROLE, and that role's USAGE grant on the project object had just quietly ceased to exist.

So every triggered build failed. Not slowly, not partially: each one died in two or three seconds with "does not exist or not authorized". Data kept landing in RAW, the stream kept firing the task, the task kept failing. This happened eleven times over two days, and then Snowflake did exactly what it is configured to do and auto-suspended the task after the consecutive-failure threshold. From that point the prod models were frozen, and nothing anywhere said anything.

The ops dashboard showed it, in the sense that a graveyard shows things. Every failure was sitting right there in TASK_HISTORY with a clear error message, but a dashboard only tells you what you ask it, and for two days nobody asked. The fix, when I finally looked, took two GRANT statements and a resume. The lesson took longer, and this chapter is that lesson: the platform needed a way to speak first.

§ 1. What the outage actually taught

The obvious patch went in first: the deploy target in dbt-pipelines/Makefile now re-grants USAGE to DBT_RUNNER_ROLE immediately after every snow dbt deploy, so a bare deploy can no longer disarm the triggers. That closes this specific hole. It does nothing about the shape of the failure, which is the part worth generalizing.

The shape was: a fully instrumented system failed loudly into its own telemetry and no human heard it, because reading telemetry was a pull. Eleven recorded failures, a rich error message on every one, an auto-suspension at the end, and total silence. Any failure mode I have not imagined yet will follow the same script unless something pushes.

§ 2. In-process, not a sweep

The standard answer is a sweep: a scheduled job that reads TASK_HISTORY every ten minutes and pages on anything red. I went the other way. In this platform, the thing that fails is the thing that pings.

The reasoning is about the cascade. An auto-suspension is never the first event; it is preceded by a run of individual failures (eleven, in my case) that each had a live session and a full error message in hand at the moment they died. Alerting at the failure level means the channel hears about the problem at failure #1, within seconds, not at the bottom of the cascade or at the next tick of a polling job. It also means zero new scheduled infrastructure: no sweep task, no sweep warehouse, no sweep that can itself die silently.

There are exactly two senders, one per failure domain. On the ingestion side, dlt-pipelines/pipelines/common/alerts.py is a small module the batch runner wraps around every pipeline run, and also around registry resolution, because a spec that fails validation dies before any run record is written and would otherwise vanish. On the dbt side, the trigger procedure SP_DBT_BUILD() in dlt-pipelines/sql/sources/nfl/05_dbt_trigger.sql (and its siblings per sport) grew an EXCEPTION handler that pings and then re-raises, so TASK_HISTORY and the auto-suspend counter see exactly what they saw before the handler existed. The alert is a side effect, never a change in behavior.

§ 3. Delivery with zero infrastructure

This entire platform runs inside one Snowflake account, and I was not going to break that rule for alerting. No Lambda, no cron box, no container with Slack egress. Snowflake has native webhook notification integrations, and they are enough.

Three objects, all in dlt-pipelines/sql/ops/09_alerting.sql: a secret, an integration, and a latch table. The secret holds the Slack webhook path, and only the path. Snowflake allowlists webhook hosts per provider, so for Slack the integration's URL must literally start with https://hooks.slack.com/services/, and the SNOWFLAKE_WEBHOOK_SECRET placeholder substitutes the bound secret into it at send time. The secret's value is therefore only the part after /services/, never a full URL, and it never leaves the account: no container carries it, and no container needs network access to Slack at all.

Listing 1 · The secret and the integration, trimmed from sql/ops/09_alerting.sql

CREATE SECRET IF NOT EXISTS DLT_DB.OPS.SLACK_ALERTS_WEBHOOK
  TYPE = GENERIC_STRING
  SECRET_STRING = 'T00000000/B00000000/XXXXXXXXXXXXXXXXXXXXXXXX';
  -- real value set out-of-band via ALTER SECRET, never in a file

CREATE OR REPLACE NOTIFICATION INTEGRATION SLACK_ALERTS_INT
  TYPE = WEBHOOK
  ENABLED = TRUE
  WEBHOOK_URL = 'https://hooks.slack.com/services/SNOWFLAKE_WEBHOOK_SECRET'
  WEBHOOK_SECRET = DLT_DB.OPS.SLACK_ALERTS_WEBHOOK
  WEBHOOK_BODY_TEMPLATE = '{"text": "SNOWFLAKE_WEBHOOK_MESSAGE"}'
  WEBHOOK_HEADERS = ('Content-Type' = 'application/json');

The secret is only the path after /services/; the integration substitutes it into the URL at send time.

Sending is one function call over a session the sender already has. The dlt container is already connected to Snowflake to load data; the dbt trigger procedure is already running inside one. Both just call:

Listing 2 · The send call

CALL SYSTEM$SEND_SNOWFLAKE_NOTIFICATION(
  SNOWFLAKE.NOTIFICATION.TEXT_PLAIN(
    SNOWFLAKE.NOTIFICATION.SANITIZE_WEBHOOK_CONTENT(
      'FAILED nfl_stats: ...error snippet...')),
  SNOWFLAKE.NOTIFICATION.INTEGRATION('SLACK_ALERTS_INT'));

SANITIZE_WEBHOOK_CONTENT strips placeholder tokens server-side, so error text cannot smuggle the secret out through the message body.

Hard-Won Fact

CREATE NOTIFICATION INTEGRATION validates the webhook URL with the secret substituted. A free-text placeholder like "set-me-later" fails the create with "WEBHOOK_URL ... is invalid. Verify whether secret replacement makes it invalid". The placeholder must be shaped like a real Slack path (T.../B.../x...), which is why Snowflake's own docs example secret looks like T00000000/B00000000/XXX. That dummy shape is load-bearing.

Hard-Won Fact

The call returning "Enqueued notifications" proves nothing reached Slack. Delivery is async, and a bad secret or a revoked webhook fails silently after the enqueue. Verify in the channel, and confirm with INFORMATION_SCHEMA.NOTIFICATION_HISTORY(), which keeps a 14-day lookback of actual delivery outcomes.

§ 4. The noise policy: transitions plus recovery

A channel that pings on every failure of a repeating schedule trains you to mute it, and a muted channel recreates the silent outage with extra steps. So the third object in ops/09 is DLT_DB.OPS.ALERT_STATE: one row per alert scope, latest status only. A scope is a pipeline name, a dbt_build_<sport>, or runner for deaths before a pipeline is even resolved. It is a dedup latch, not a history; TASK_HISTORY already holds the history.

The rule both senders implement is the same and is small enough to be a pure function. This is the Python side, unit-testable without a connection:

Listing 3 · The transition rule, from pipelines/common/alerts.py

def decide(prev_status: str | None, ok: bool) -> str | None:
    """The transition rule: 'fail', 'recover', or None (stay silent)."""
    if not ok:
        return None if prev_status == "failing" else "fail"
    return "recover" if prev_status == "failing" else None

An unseen scope that fails does ping: "first failure ever" is exactly a healthy-to-failing transition.

The first failure of a streak pings FAILED <scope> with a flattened, truncated error snippet. Repeats update the latch silently. The first success after a failing streak pings RECOVERED <scope>, which matters as much as the failure ping: it closes the incident without anyone querying anything. A daily pipeline failing for a week costs one ping, not seven. A healthy week costs zero, and a channel that only speaks when something changes is a channel you keep unmuted.

One more piece of noise discipline: the Python sender is a no-op unless DLT_ALERTS=1, which only the prod job template sets. Laptop runs, dev containers, and CI cannot page the channel, and they do not even know the module exists.

§ 5. Best-effort, enforced

The alert path must never mask the error it reports, and it must never fail a run that succeeded. Both senders treat alerting as strictly best-effort. In Python, every exit from report() is caught and logged as a warning, and the send happens before the latch write: if the write then fails, the worst case is a duplicate ping next run, which beats a latch claiming "alerted" about a ping that never left.

The SQL side is where this gets structural. The EXCEPTION handler captures SQLERRM first (the nested block's own statements can replace the active exception context), wraps the entire ping-and-latch sequence in a nested block that swallows everything, and only then re-raises the original error:

Listing 4 · SP_DBT_BUILD's handler, trimmed from sql/sources/nfl/05_dbt_trigger.sql

EXCEPTION
  WHEN OTHER THEN
    LET err VARCHAR := LEFT(COALESCE(SQLERRM, 'unknown error'), 400);
    BEGIN
      LET prev VARCHAR := (SELECT MAX(STATUS) FROM DLT_DB.OPS.ALERT_STATE
                           WHERE SCOPE = 'dbt_build_nfl');
      IF (prev IS NULL OR prev <> 'failing') THEN
        CALL SYSTEM$SEND_SNOWFLAKE_NOTIFICATION(
          SNOWFLAKE.NOTIFICATION.TEXT_PLAIN(
            SNOWFLAKE.NOTIFICATION.SANITIZE_WEBHOOK_CONTENT(
              'FAILED dbt_build_nfl: ' || :err)),
          SNOWFLAKE.NOTIFICATION.INTEGRATION('SLACK_ALERTS_INT'));
      END IF;
      MERGE INTO DLT_DB.OPS.ALERT_STATE ...   -- latch to 'failing'
    EXCEPTION
      WHEN OTHER THEN
        NULL;   -- broken alert plumbing must never mask the dbt error
    END;
    RAISE;      -- TASK_HISTORY and auto-suspend see the original failure

Ping on the transition, swallow anything the alert path itself throws, then re-raise the real error unchanged.

That final RAISE is the contract with the rest of the platform. The task still fails, the failure still lands in TASK_HISTORY with its error message, and the consecutive-failure counter still ticks toward auto-suspension. If the alerting objects were dropped tomorrow, the builds would behave identically; they would just go back to failing quietly.

Hard-Won Fact

A task session runs its owner's PRIMARY role alone. Interactive testing carries secondary roles, so proving the send works from your own session proves nothing about whether it works from a task. Smoke-test the send as each worker role itself (USE ROLE ..., then the bare SYSTEM$SEND_SNOWFLAKE_NOTIFICATION call) before shipping code that depends on the USAGE grants being right. This is the same lesson the event-table plumbing paid for earlier, learned again here on purpose rather than by accident.

§ 6. The blind spots, stated plainly

In-process alerting has a boundary, and I would rather name it than pretend it away. A container that never starts sends nothing, because the code that would ping never ran. A schedule that is dead without failing (a suspended task, a stream gone stale) also sends nothing, for the same reason: no failure event means no process, and no process means no ping. Both are known, both are accepted for now, and both belong to a future sweep that reads the telemetry and asks "did the things that should have run actually run?" That sweep can be lazy and infrequent, because it only has to catch absence.

Everything else, which is to say every failure that involves code actually failing, pages the channel within seconds of the first occurrence, recovers with a second ping, and stays silent in between. The outage ran two days on eleven failures without a word. The same outage today would be one Slack message, about three seconds after the first build died.
