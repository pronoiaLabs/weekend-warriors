Chapter 2

dbt builds that fire when data lands

streams + triggered tasks, no orchestrator

Ask how to run dbt right after ingestion finishes and the answer you will get, almost every time, is an orchestrator. Airflow, Dagster, Prefect: a scheduler that lives outside the warehouse, watches the load job, and kicks off the build when it goes green. I want to make the opposite case. In this project, dbt rebuilds the NFL models within a couple of minutes of new data landing, and there is no orchestrator anywhere. The warehouse watches itself. The whole mechanism is one stream, one triggered task, one stored procedure, and it lives in a single SQL file: dlt-pipelines/sql/sources/nfl/05_dbt_trigger.sql.

§ 1. The usual answer is an orchestrator

The standard architecture puts a third system between ingestion and modeling. The loader finishes, tells the orchestrator, and the orchestrator tells dbt. That works, but now you own a scheduler: its hosting, its credentials into the warehouse, its retry semantics, its opinion about what "done" means. For a stack whose whole premise is that everything runs inside the Snowflake account (Chapter 1 covered getting dlt itself in there), bolting an external brain on the side just to say "data arrived, go" felt like giving up the premise at the last step.

The unexpected answer is that Snowflake already has both halves of the problem solved as native objects. Streams answer "did new data arrive?" and triggered tasks answer "run this when it does." What is left is wiring them together carefully, and the care is the interesting part.

§ 2. The signal is free, and structurally correct

Every dlt pipeline that loads NFL_PROD_DB.RAW finishes a successful load the same way: it inserts one row into RAW._DLT_LOADS, dlt's own bookkeeping table. The crucial property is when that insert does not happen. A failed load never writes to _DLT_LOADS. So an append-only stream on that table is a perfect "new good data" signal, for free. Failed loads can never trigger a rebuild, and not because anyone wrote a filter that checks a status column. The event simply does not exist. Correctness by construction beats correctness by filtering every time, because there is no predicate to get wrong later.

The stream is append-only deliberately: I only care about inserts, and dlt only inserts. One wrinkle worth knowing: streams need change tracking enabled on the source table, and creating a stream as a non-owner does not enable it. The file sets CHANGE_TRACKING = TRUE explicitly, as the table's owner role, before the stream exists.

§ 3. A task with no schedule

The consumer is a Snowflake task that has no SCHEDULE clause at all. Instead it declares a WHEN condition on the stream, which turns it into a triggered task: it runs when the stream has data and sits idle otherwise, at zero cost. No cron expression is guessing at when games finish.

Listing 1 · The stream and the triggered task, trimmed

CREATE STREAM IF NOT EXISTS NFL_PROD_DB.OPS.DBT_LOADS_STREAM
  ON TABLE NFL_PROD_DB.RAW._DLT_LOADS APPEND_ONLY = TRUE;

CREATE OR ALTER TASK NFL_PROD_DB.OPS.DBT_BUILD_NFL
  WAREHOUSE = DBT_WH
  USER_TASK_MINIMUM_TRIGGER_INTERVAL_IN_SECONDS = 900
  USER_TASK_TIMEOUT_MS = 3600000
  WHEN SYSTEM$STREAM_HAS_DATA('NFL_PROD_DB.OPS.DBT_LOADS_STREAM')
AS
  CALL NFL_PROD_DB.OPS.SP_DBT_BUILD();

No schedule anywhere: the task exists to react, not to poll on my behalf.

The minimum trigger interval is doing quiet load-shaping work. On a Sunday afternoon, several pipelines land within minutes of each other: games, then stats, then standings. Without the interval, each landing could start its own dbt build. With a 900-second floor, everything that arrives inside the window accumulates in the stream, and the next fire drains all of it into one build. A load that lands mid-build is not lost either; the stream holds it and the task simply re-triggers after the current run finishes.

Hard-Won Fact

The 900-second minimum trigger interval turns a burst of loads inside the window into one build that drains all of them. Verified directly: three inserts into _DLT_LOADS within the window produced exactly one task run, and its audit table showed all three loads drained by that run.

§ 4. The procedure: drain first, always

The procedure the task calls does exactly two things, in an order that matters more than anything else in this chapter. First it drains the stream, then it builds. The drain is a plain INSERT ... SELECT from the stream into an audit table, DBT_TRIGGER_LOADS, which records which loads triggered which build. That looks like bookkeeping. It is not. In Snowflake, a stream only advances its offset when it is consumed by DML. Merely selecting from it changes nothing.

Hard-Won Fact

Drain-first is mandatory, not an audit nicety. A stream that is only read keeps SYSTEM$STREAM_HAS_DATA returning true, so the triggered task re-fires every interval forever, billing the warehouse each time. Measured during development: 4 fires in 90 seconds before the DML drain went in.

Listing 2 · Drain, then build, trimmed from SP_DBT_BUILD

-- Drain FIRST. This INSERT is the stream consumption; without it
-- the task re-fires every interval forever.
INSERT INTO NFL_PROD_DB.OPS.DBT_TRIGGER_LOADS
    (LOAD_ID, PIPELINE, STATUS, INSERTED_AT, DRAINED_AT)
  SELECT LOAD_ID, SCHEMA_NAME, STATUS, INSERTED_AT, CURRENT_TIMESTAMP()
  FROM NFL_PROD_DB.OPS.DBT_LOADS_STREAM;
drained := SQLROWCOUNT;

-- SYSTEM$STREAM_HAS_DATA tolerates false positives; don't build on one.
IF (drained = 0) THEN
  RETURN 'no-op: stream was empty';
END IF;

EXECUTE IMMEDIATE 'EXECUTE DBT PROJECT DLT_DB.DEPLOY.CORTEX_LIFECYCLE_NFL'
  || ' ARGS = ''run'''
  || ' ENVIRONMENT = ''prod'''
  || ' ENV_VARS = (''DBT_BUILD_ID'' = ''' || build_id || ''')';

The zero-row guard exists because SYSTEM$STREAM_HAS_DATA is documented to allow false positives.

Three details in those few lines each earned their place. The ENVIRONMENT = 'prod' is explicit because the dbt project object defaults to dev; omit it and the task happily, silently, builds the wrong target with no error to tell you so. The build_id is a UUID minted at the top of the procedure and passed through ENV_VARS, from where a dbt macro folds it into every query's QUERY_TAG, so every warehouse query of every build is attributable afterward. And the whole statement goes through EXECUTE IMMEDIATE because the ENV_VARS clause validates its values at CREATE PROCEDURE time and rejects a Scripting bind variable; assembling the literal is the workaround, and it is safe here because the value being inlined is a self-minted UUID.

One more constraint hides off-screen: EXECUTE DBT PROJECT requires a caller's-rights procedure, and concurrent executions against a single project object are unsupported. Since each sport's trigger can fire at the same time, each sport gets its own project object (CORTEX_LIFECYCLE_NFL, CORTEX_LIFECYCLE_NCAAF, and so on), all deployed from one source tree. Deploying a sport's object is the release step: the trigger always runs whatever that object holds.

§ 5. Both outcomes land somewhere useful

On success, the procedure writes one row to DLT_DB.OPS.DBT_BUILDS (build id, environment, how many loads were drained, the query id of the EXECUTE DBT PROJECT statement) and then stamps the task's history row via SYSTEM$SET_RETURN_VALUE, so the build id is readable straight out of TASK_HISTORY.

Hard-Won Fact

A procedure's RETURN string never reaches TASK_HISTORY.RETURN_VALUE; it reads back as null. Only SYSTEM$SET_RETURN_VALUE populates it, and that function demands a constant argument: pass it a bind or a concatenation and you get a compilation error, so the call is assembled as a literal via EXECUTE IMMEDIATE. It also errors when the procedure runs outside a task, which is why the call sits inside its own guard for manual smoke tests.

On failure, the procedure does something better than handling the error: it lets it raise. A partial dbt failure surfaces as a real SQL error, the task run fails, TASK_HISTORY.ERROR_MESSAGE carries the message, and the failure counts toward Snowflake's automatic suspend-after-N-failures threshold, so a persistently broken build eventually stops billing the warehouse on its own. What happens next, turning that failure into a message a human actually sees, is Chapter 3's story.

Listing 3 · The harvest child, gated on build success

CREATE OR ALTER TASK NFL_PROD_DB.OPS.DBT_HARVEST_NFL
  WAREHOUSE = DBT_WH
  AFTER NFL_PROD_DB.OPS.DBT_BUILD_NFL
AS
  CALL DLT_DB.OPS.SP_DBT_HARVEST();

Task-graph semantics do the gating: a child AFTER a root runs only when the root run succeeded.

That child task harvests query-level telemetry (the tagged queries and their operator stats) after each build. Making it a child rather than a second trigger buys the gating for free: it never runs after a failed build, and a harvest failure fails its own task run, never the build. One footgun in this shape: CREATE OR ALTER TASK leaves tasks suspended, and a resumed root with a suspended child silently skips the child, so the file resumes the child before the root, every time.

§ 6. No scheduler knows dbt exists

Step back and look at the chain: a container loads the API into RAW, dlt records the success, the stream sees the insert, the task fires, the procedure drains and builds, models refresh in PREP, CORE, and ANALYTICS. End to end, that typically completes within a minute or two of the load landing, and every link is a Snowflake object owned by a role, versioned in one SQL file, applied idempotently. There is no cron expression estimating when data arrives, no orchestrator holding warehouse credentials, no scheduler anywhere that knows dbt exists.

The operational surface is correspondingly small. The kill switch is one statement, ALTER TASK NFL_PROD_DB.OPS.DBT_BUILD_NFL SUSPEND: ingestion continues untouched, the stream accumulates, and everything drains into one build on resume. Adding a sport is the same file with the names changed. I am not arguing orchestrators are never worth it; cross-system DAGs with fan-in from a dozen sources are a different problem. But "run dbt when the load succeeds" is not that problem, and the warehouse turns out to be the right tool for watching itself.
