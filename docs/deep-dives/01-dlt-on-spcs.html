Chapter 1

Deploying dlt to Snowpark Container Services

how a Python pipeline becomes a container Snowflake runs

Hear me out: the place your data lands can also be the place your ingestion code runs. This project loads football data with dlt, and every scheduled run happens inside the Snowflake account itself, as a container on Snowpark Container Services. No VPS, no Lambda, no cron box that everyone forgets exists. If you have a side project with Python jobs and a Snowflake account, this chapter is the case that you may already own all the infrastructure you need.

§ 1. The shape of the problem

A dlt pipeline is just Python. It calls a REST API, normalizes what comes back, and loads it into a destination. The hard part was never the code, it was always the question of where the code runs at 09:00 UTC when your laptop is closed. The usual answers are a VPS you now administer, or a serverless function with its own packaging format, its own secrets manager, and its own way of authenticating back to the warehouse.

The answer I did not expect is that the warehouse runs containers. Snowpark Container Services (SPCS) has two modes: long-lived services, and job services that start, run to completion, and exit. A batch pipeline is exactly the second shape. There is no service to babysit, no health check to write, and compute is billed while the job runs on its pool. You launch a job, the container does its work, the container goes away. That is the whole operational model, and it maps onto a scheduled load with nothing left over.

The rest of this chapter is the path from python -m pipelines.batch.run on a laptop to that same module running as a container Snowflake launches. Four pieces: one image, one job spec template, one egress grant per source API, and a short deploy flow.

§ 2. One image, config-agnostic

The Dockerfile at dlt-pipelines/deploy/spcs/Dockerfile is deliberately boring. It ships the pipelines package and its dependencies, and its entrypoint is the same module you run locally. The pipeline name arrives as the container argument.

Listing 1 · the whole runtime image

FROM python:3.11-slim

COPY --from=ghcr.io/astral-sh/uv:0.11.2 /uv /uvx /bin/

WORKDIR /app
COPY pyproject.toml ./
COPY pipelines/ ./pipelines/
RUN uv pip install --system --no-cache "."

COPY .dlt/config.toml ./.dlt/config.toml

ENTRYPOINT ["python", "-m", "pipelines.batch.run"]

deploy/spcs/Dockerfile, trimmed to the statements: same entrypoint as a laptop run, pipeline name passed as the argument.

The important design decision is what the image does not contain: pipeline definitions. At run time the container reads its spec (endpoints, pagination, write disposition, target database stem) from a registry table in the account's control plane, DLT_DB.OPS.PIPELINE_REGISTRY. The YAML files under dlt-pipelines/pipelines/batch/registries/ are the source of truth in git and the local-dev fallback, and a sync step pushes them into that table. So adding or editing a pipeline is an INSERT, not an image rebuild. I rebuild the image only when code or dependencies change, which in practice is rarely.

The image itself lives in an image repository inside the same Snowflake account (DLT_DB.DEPLOY.IMAGES). One detail that will bite an Apple Silicon laptop: SPCS compute pools are x86_64, so the image must be built linux/amd64. Building it emulated under QEMU works but is painfully slow, which is a good excuse to let CI do it on an amd64 runner.

§ 3. The job spec template

Between the image and a running job sits a small YAML spec, dlt-pipelines/deploy/spcs/dlt_job.tmpl.yaml. It is a Jinja template with a handful of placeholders filled per pipeline: the pipeline name, the destination database, and the secret binding. One template plus one image drives every pipeline in the fleet.

Listing 2 · the env and secrets block of the job spec

spec:
  containers:
    - name: dlt
      image: /DLT_DB/DEPLOY/IMAGES/dlt-pipeline:latest
      args:
        - {{ pipeline }}
      env:
        DESTINATION__SNOWFLAKE__CREDENTIALS__AUTHENTICATOR: oauth
        DESTINATION__SNOWFLAKE__CREDENTIALS__DATABASE: {{ database }}
        DESTINATION__SNOWFLAKE__CREDENTIALS__WAREHOUSE: DLT_WH
        SNOWFLAKE_DATABASE: DLT_DB
        DLT_REGISTRY_SOURCE: auto
      secrets:
        - snowflakeSecret: {{ secret }}
          secretKeyRef: secret_string
          envVarName: {{ env_var }}

deploy/spcs/dlt_job.tmpl.yaml, trimmed: the authenticator is oauth with no token anywhere in sight, and the API key arrives through the secrets block.

Two things in that listing carry most of the security story. First, notice there is no Snowflake credential at all. The authenticator says oauth, and the token comes from Snowflake itself: SPCS mounts a short-lived OAuth session token into every container at /snowflake/session/token. The code in dlt-pipelines/pipelines/common/snowflake_session.py decides which world it is in by checking whether that file exists. If it does, connect with the mounted token; if not, fall back to the usual env vars a laptop or CI would set. The signal is the file, deliberately, because a file at that path is something only the SPCS runtime can produce.

Hard-Won Fact

SPCS detection keys on the token file, never an env var. An environment variable like RUNNING_IN_SPCS=1 is one export away from being faked on any laptop; the mounted token at /snowflake/session/token cannot be conjured outside a real container. Detecting the platform by the one artifact only the platform can produce means the oauth code path is unreachable from anywhere else.

Second, the source API key. It is never in the image, never in git, never in the registry YAML. It lives as a Snowflake SECRET object (sql/sources/nfl/03_secrets.sql creates it, an ALTER sets the real value), and the spec's secrets: block mounts it into the container as whatever env var the pipeline's config expects. dlt resolves a secret:sources.nfl.api_key reference from the env var SOURCES__NFL__API_KEY, so the binding is three lines of spec, not a line of code.

Hard-Won Fact

Because the secret binds at the spec layer, the container image is credential-free by construction. The same image runs the NFL pipelines, the WNBA pipelines, or any future league's, and the only thing that changes is which SECRET object the spec names. There is nothing to rotate in an image, nothing to scrub from a layer, and a leaked image leaks no keys.

§ 4. Egress is opt-in

An SPCS container has no network egress by default. None. It can talk to Snowflake through the ambient session, and that is it. Reaching an external API takes two objects: a NETWORK RULE naming the exact host and port, and an EXTERNAL ACCESS INTEGRATION wrapping that rule, granted to the roles that launch jobs. One pair per source API, kept in that source's own SQL directory.

Listing 3 · granting exactly one host

CREATE OR REPLACE NETWORK RULE DLT_DB.OPS.NFL_API_EGRESS
    MODE       = EGRESS
    TYPE       = HOST_PORT
    VALUE_LIST = ('api.balldontlie.io:443');

CREATE OR REPLACE EXTERNAL ACCESS INTEGRATION NFL_API_EAI
    ALLOWED_NETWORK_RULES = (DLT_DB.OPS.NFL_API_EGRESS)
    ENABLED = TRUE;

GRANT USAGE ON INTEGRATION NFL_API_EAI TO ROLE DLT_DEV_ROLE;
GRANT USAGE ON INTEGRATION NFL_API_EAI TO ROLE DLT_LOADER_ROLE;

sql/sources/nfl/02_external_access.sql, trimmed: the port is required in VALUE_LIST, and a bare hostname is not enough.

I have come to like this inversion. On a VPS the default is everything and you subtract; here the default is nothing and you add one host. The integration is then named on each job launch, so the grant travels with the pipeline rather than with the machine. The failure mode, though, took me a while to read correctly the first time.

Hard-Won Fact

Egress denied looks exactly like the API being down. A container missing its external access integration does not get a crisp permission error: the connection just times out, which surfaces as retries and eventually a request failure that reads like a provider outage. Before blaming the API's status page, check that the job was launched with the EAI attached. The registry here requires every scheduled pipeline to declare its external_access up front for exactly this reason.

§ 5. The deploy flow

With those pieces in place, deploying is three ships and one statement. Build the image and push it to the account's image repository. Sync the registry YAML into the control-plane table. Upload the spec template to a Snowflake stage (@DLT_DB.DEPLOY.SPECS). After that, launching any pipeline is a single SQL statement.

Listing 4 · one statement to run a pipeline

EXECUTE JOB SERVICE
  IN COMPUTE POOL DLT_POOL
  NAME = dlt_job_nfl_reference
  EXTERNAL_ACCESS_INTEGRATIONS = (NFL_API_EAI)
  FROM @DLT_DB.DEPLOY.SPECS
    SPECIFICATION_TEMPLATE_FILE = 'dlt_job.tmpl.yaml'
    USING (
      pipeline => 'nfl_reference',
      database => 'NFL_PROD_DB',
      secret   => 'DLT_DB.OPS.NFL_API_KEY',
      env_var  => 'SOURCES__NFL__API_KEY'
    );

The USING clause fills the template's placeholders; note EXTERNAL_ACCESS_INTEGRATIONS must come before FROM, which is a SQL compilation error the other way around.

That statement pulls the image from the account's repository, renders the spec with the USING values, mounts the session token and the secret, attaches the egress grant, runs the container to completion on the pool, and releases it. Wiring that statement onto a schedule is a Snowflake Task, and Tasks have their own sharp edges, which is the next chapter's story.

Here is the payoff, and the reason I think this pattern deserves a look for any side project already sitting on Snowflake: the laptop only ever ships artifacts. It pushes an image, uploads a spec, syncs a table. Execution, credentials, network policy, and scheduling all live inside the account, and nothing outside it ever runs the code.
