Internal reference · companion to the enrichment columns doc

The APP layer plan, and the API that keeps up

What each page mart looks like today, exactly which enrichment columns it gains, the new marts, and — because the dashboard reads APP through explicit column contracts — the precise API touch points that keep everything intact while we build.

How APP and the API fit together

The serving path today: dbt builds page-shaped marts into NFL_PROD_DB.APP (long format, parameters as columns); a dlt pipeline (app-copy-registry.yml) replaces each mart into Postgres app.app_copy; the FastAPI service reads Postgres by default (the swap has landed — db.py is dual-backend with Snowflake retained for fixture capture and rollback). Curated pages select through pydantic row models; the Explorer is fully dynamic.
  • APP tables adopt the same naming convention as DIM/FACTS: the schema carries the role, physical names drop the app_ prefix, two words minimum — APP.GAME_SLATE, APP.PROP_BOARD, APP.LINE_HISTORY; explore sheets keep an EXPLORE_ family prefix (APP.EXPLORE_PLAYER_GAMES). dbt model names stay app_* via the same generate_alias_name macro (folder strip + overrides: app_game_prop_board → PROP_BOARD, app_player_defense_weeks → DEFENDER_WEEKS, and app_play_log → PLAY_FEED, because dev collapses schemas and a bare PLAY_LOG would collide with the FACTS alias for fact_play). Unlike DIM/FACTS, the API pins physical names, so the rename touches four places in lockstep: the profiles tables map, the Postgres app-copy-registry.yml, the fixtures/schema fixture filenames + capture SELECTION keys, and the Explorer's f"app_explore_{sheet.id}" prefix (becomes explore_{id}). The contract tests then verify the whole chain. Section headers below show the physical name; grain lines name the dbt model; prose keeps dbt model names.
  • What changes underneath: the marts re-point their ref()s from retired vendor facts to the wide facts — which is free, since the wide facts keep the same model names and keys. APP enrichment is then mostly "select more columns from the same ref".
  • Two conventions every addition must respect: the vendor-NULL row (game-level columns belong on it, line-level columns don't) and knowability (form windows strictly pre-kickoff; projections only from is_pre_kickoff snapshots; live status columns are serving-only, never history).

The additive rules verified against the API code — what breaks, what doesn't

New column on an existing mart
Nothing breaks. Tiles select only known columns (COLUMNS = tuple(Row.model_fields)), extra mart columns are ignored, and the Postgres replace load carries new columns automatically. To surface a column: add the field to the tile's pydantic row model (COLUMNS follows), mirror it in web/src/api/sports/types.ts, use it in the page, then make fixtures — the schema fixtures are what test_profiles_contract.py asserts against, so a stale fixture fails CI, which is the safety net working.
Renaming or dropping a mart column breaks the SELECT immediately — the enrichment plan is additive on APP precisely to avoid that.
The LINE_FIELDS slice — the one sharp edge
tiles/slate.py and tiles/teams.py blank a game's line fields on the vendor-NULL fallback using a positional slice of COLUMNS: vendor … total_result. So placement in the row model is semantic:
line-level column → inside the slice
game/team-level column → after total_result
A line column accidentally placed after the sentinel leaks another book's value onto a no-line card; a game column placed inside gets wrongly blanked. Every addition below states its placement.
The Explorer — zero-code additions
Explore sheets read their live column list, so a new column on any app_explore_* table appears in the catalog, grid, filters and sort with no API or frontend change. Requirements: the sheet keeps row_id, and the sheet SQL itself names the column (sheets are curated flat selects — one line per column). VARIANT/ARRAY columns need a parse_variant field_validator on curated pages (Postgres lands them as text).

API plan · the Postgres copy gate

A new mart does not exist for the API until it's in the copy registry Live reads hit Postgres app.app_copy, fed by dlt-pipelines/pipelines/batch/registries/app-copy-registry.yml — an explicit list of all 20 NFL marts ("do not SELECT * from the schema"), replace-loaded. New marts (app_team_situation, app_explore_team_situations) must be added there or the API throws missing-relation errors even though the dbt model built fine in Snowflake. New columns ride the replace loads automatically, with one caveat: Snowflake VARIANT/ARRAY lands as text in Postgres, so any new array column surfaced on a curated page needs a field_validator(..., mode="before") calling db.parse_variant (the pattern stat_last3 and last_results already use).
